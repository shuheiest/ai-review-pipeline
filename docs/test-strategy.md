# テスト方針

テストは「単体テスト」と「シナリオテスト」の2種類で書く。どちらもVitestで実行し、PRのたびにCIで自動で走らせる。テストケースそのものは `docs/test-cases.md` に従う。

## 0. なぜ test-cases.md を分けているのか

`docs/test-cases.md` は、**何が正しい動きかを、人間が決めるための文書**です。テストのコードとは分けて、本人が書きます。理由は3つです。

1. **正しさの基準を、実装から独立させるため**：実装を書いた側（AI）がテストのケースも決めると、実装の思い込みがそのままテストに入り、間違いに気づけない。ケースを先に人間が決めておけば、テストは実装ではなく仕様を確かめるものになる
2. **人間とAIの役割を分けるため**：「何を確かめるか」は人間が設計し、「どう確かめるか（テストのコード）」はAIが書く。この分担を、文書とコミットの履歴で残す
3. **レビューで追えるようにするため**：各ケースにIDを付け、テスト名と対応させる。AIレビューと人間のレビューで、「どのケースが確かめられていないか」をすぐに見つけられる

このため、AIは `docs/test-cases.md` を編集しない。ケースが足りない・間違っていると思ったら、テストのコードで勝手に補わず、提案として報告する。

## 1. 2種類のテストの違い

| | 単体テスト | シナリオテスト |
|---|---|---|
| 目的 | ルールが正しいかを、部品ごとに確かめる | 利用者の一連の操作が、APIを通して正しく動くかを確かめる |
| 対象 | `src/server/domain/` の純粋な関数（ステータスの流れ、入力チェック） | Honoのアプリ全体（`routes → usecase → domain → repository`） |
| データベース | 使わない | テスト用のSQLiteを使う。テストごとに空の状態から始める |
| 呼び出し方 | 関数を直接呼ぶ | Honoの `app.request()` でHTTPリクエストを送る |
| 置き場所 | テスト対象と同じフォルダに `*.test.ts` | `tests/scenarios/*.test.ts` |
| 速さ | とても速い。数を多く書く | 少し遅い。代表的な流れに絞る |

## 2. 単体テストの書き方

- 1つのテストでは、1つのことだけを確かめる
- 境界の値を必ず含める（例：タイトルの0文字・1文字・50文字・51文字）
- 許される場合と、許されない場合の両方を書く
- 同じ形のケースが並ぶときは、`it.each` で表にして書く
- 現在日時に依存する処理（期限が過去かどうか、`completedAt`）は、Vitestの `vi.useFakeTimers()` と `vi.setSystemTime()` で日時を固定する

## 3. シナリオテストの書き方

- テスト名は、利用者の操作の流れとして書く（例：「タスクを作成し、着手して、完了すると、完了日時が入る」）
- 1つのシナリオで、複数のAPIを順番に呼び、途中の状態も確かめる
- HTTPのステータスコードと、レスポンスの中身の両方を確かめる（例：409と、エラーの内容）
- テストの間でデータを共有しない。各テストの前にデータベースを空にする

## 4. 共通のルール

- テストの説明（`describe` / `it` の名前）は日本語で書く
- `docs/test-cases.md` の各ケースに付けたID（例：`ST-01`）を、テスト名の先頭に入れる。どのケースのテストかを追えるようにするため
- 「Arrange（準備）・Act（実行）・Assert（確認）」の順に書き、間に空行を入れる
- テストのコードにも、`docs/spec.md` の「コードのルール」（200行、複雑度5、`any` 禁止）を適用する
- 実装に合わせてテストを書き換えない。テストが落ちたら、まず実装を疑う。テストケースが間違っていると思ったら、作業を止めて報告する

## 5. 今回はやらないこと

- ブラウザを動かす画面のテスト（E2Eテスト）。最小版の完成後に、必要なら追加する
